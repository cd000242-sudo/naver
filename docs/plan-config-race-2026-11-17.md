# 설정 저장·읽기 경합 수정 계획 (2026-11-17)

상태: **계획만. 코드는 아직 건드리지 않았다.** 사장님 승인 뒤 릴리즈 4번으로 나눠 진행한다.

## 한 줄 결론

`src/configManager.ts` 는 쓰는 도중에 읽으면 옛 값·빈 값이 돌아오고, 그 상태에서 부분 저장이 이어지면 설정 일부가 사라질 수 있다. 더 큰 문제는 2026-09-02 스냅샷 수정 뒤로 **보존 목록(PRESERVE_KEYS) 복구값과 라이선스 자격증명 삭제가 디스크에 반영되지 않는 것으로 보인다**는 점이다(경합 없이도 — 코드 추적 결과이며 시험으로는 아직 확인하지 않았다).

## 어떻게 알았나

- 실측(2026-11-17): 격리 프로필로 앱을 처음 켜고 main 의 `config:get` / `config:set` 처리기를 감싸 순서를 기록했다.
  - 기동 1초 안에 `config:get` 약 19회, `config:set` 3회(3필드·1필드·26필드)가 겹친다.
  - 3필드 저장이 146ms 에 들어가 459ms 에 나왔는데 **응답에 방금 쓴 필드가 없었다**(직후 읽기에는 있음 = 파일은 맞게 쓰임).
  - 다른 저장이 진행 중(458~503ms)일 때 460ms 에 들어온 읽기가 **방금 저장된 필드가 없는 설정**을 돌려줬다.
- 코드 추적(하위 작업자, 읽기 전용): 아래 표. 시험·앱 실행은 하지 않았다.

## 수정 순서 (릴리즈 4번 — 한 릴리즈에 수정 1~3개)

**릴리즈 1 — 저장 본체가 자기 스냅샷만 본다** (`_saveConfigImpl` 만)
1. 894 이후 본체가 공유 `cachedConfig` 를 읽거나 재대입하지 않는다. 908~930 은 스냅샷 제자리 수정, PRESERVE(972·1017·1036)와 백싱크(1076~1124)는 스냅샷 기준.
2. 끝에서 스냅샷을 돌려준다. 스냅샷 시점의 계정이 지금과 같을 때만 캐시에 스냅샷을 넣는다.
- 해결: R-1, R-2, R-3, R-4, R-5.

**릴리즈 2 — 읽기가 빈 설정을 만들지 않는다**
1. `loadConfig` 의 ENOENT 아닌 실패는 2~3회 짧게 다시 읽는다. 그래도 안 되면 같은 계정의 직전 캐시를 돌려주고, 없으면 `{}` 를 돌려주되 캐시에는 넣지 않는다.
2. `ensureConfigPath` 의 첫 활성화가 한 번만 돌게 한다(경로 등록을 복사 뒤로, 또는 진행 중 Promise 공유).
- 해결: R-6 의 캐시 오염, R-7.

**릴리즈 3 — 남의 것·옛 것으로 캐시를 덮지 않는다**
1. `loadConfig` 가 시작할 때의 계정과 저장 세대를 기억하고, 둘 다 같을 때만 캐시에 넣는다(반환값은 그대로).
2. 저장 본체에서 병합 기반의 계정과 쓸 경로의 계정이 다르면 새 계정 기준으로 한 번 다시 읽어 병합한다.
- 해결: R-8, R-9, 릴리즈 1 뒤에 남는 좁은 창.

**릴리즈 4 — 원자적 쓰기**
1. 주 저장(1071)을 임시 파일에 쓰고 `_retryOnEBUSY` 로 감싼 rename 으로 바꾼다. 실패하면 임시 파일만 치우고 원본은 그대로.
2. 백싱크(1130)에 같은 방식을 쓴다.
- 릴리즈 2 가 먼저여야 한다: 지금 읽기에는 재시도가 없어 rename 순간의 EBUSY/EPERM 이 빈 설정이 된다.

**하지 않는 것**: `loadConfig` 를 저장 큐 뒤에 줄 세우기. 저장 본체가 안에서 `loadConfig` 를 기다려 교착하고, 호출이 68개 파일 192곳이라 기동이 느려지며, 계정 전환 문제(R-8·R-9)는 그대로 남는다.

## 사장님이 정할 것

1. 계정 전환 직전에 낸 부분 저장을 새 계정 파일에 적용할지, 옛 계정 파일에 쓸지. (권장: 새 계정 기준으로 다시 병합 — 새 계정 설정을 가장 덜 건드린다.)
