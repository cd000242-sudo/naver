# 정보나열을 벗어나는 법

---

## 1. 왜 지금 정보나열이 되는가 — 한 문장 + 비유

**이 앱은 "무엇을 쓸지"만 지시하고 "누구의 어떤 막힘을 푸는지"는 지시하지 않는다. 그래서 글의 단위가 '독자 1명의 문제'가 아니라 '정보 항목'이 된다.**

약국 비유가 정확하다. 손님이 "머리가 아파요"라고 하면, 좋은 약사는 *언제부터 아픈지, 공복인지, 임신 중인지*를 묻고 **한 가지를 골라준다**. 나쁜 약사는 진열대의 두통약을 A부터 Z까지 읊는다.

지금 이 앱은 후자를 시키고 있고, 그게 은유가 아니라 **글자 그대로 프롬프트에 적혀 있다** — `src/prompts/seo/base.prompt:262`:

```
- 하나의 소재 → A부터 Z까지 정리 (범위 좁히기)
```

---

## 2. 구조적 진단 (근거)

### 2-A. 경험이 못 들어오는 이유 — 문은 있는데 렌더러 4줄이 잠그고 있다

**핵심 발견: 뒷단은 이미 전부 열려 있다. 막고 있는 건 화면 쪽 4줄이다.**

경험 메모를 받는 백엔드에는 **모드 조건이 없다** — `src/main.ts:5785-5789`:
```ts
const personalExperience = String((payload.assembly as any).personalExperience || '').trim().slice(0, 4000);
if (personalExperience) {
  source.personalExperience = personalExperience;
  source.rawText = `${source.rawText}\n\n=== 작성자 직접 사용 메모 ===\n${personalExperience}`.trim();
```

근거 판정기도 SEO·홈판을 이미 지원한다 — `src/content/evidenceIntegrity.ts:64-73`:
```ts
export function hasExplicitFirstPartyEvidence(source?): boolean {
  if (meaningful(source.personalExperience)) return true;
  ...
  return /===\s*(?:작성자|사용자)\s*직접\s*(?:사용|경험)\s*메모\s*===/i.test(String(source.rawText || ''));
}
```

그런데 렌더러가 **affiliate에서만** 값을 채운다 — `src/renderer/modules/contentGeneration.ts:576-578`(URL 플로우)와 `:1128-1130`(키워드 플로우), 두 곳 모두 동일:
```ts
const personalExperience = contentMode === 'affiliate'
  ? ((document.getElementById('shopping-connect-personal-experience') as HTMLTextAreaElement | null)?.value || '').trim().slice(0, 4000) || undefined
  : undefined;
```

그 결과 13개 카테고리 프롬프트가 전부 쓰고 있는 조건절이 **SEO·홈판에서 영구히 거짓**이 된다 — `seo/base.prompt:360`, `homefeed/base.prompt:16`:
```
- 사용자 직접 경험 메모가 있을 때만 그 범위 안에서 1인칭 경험을 쓴다.
```

### 2-B. 통로가 하나 더 있는데, 앱이 그 통로를 스스로 무력화하고 있다

`hookHint`(후킹 도입부)는 **쇼핑 전용이 아니라 공통 입력 영역**에 있고 전 모드에 배선돼 있다 — `public/index.html:1281-1286`:
```html
<strong>후킹 도입부 (선택, 최대 3줄 · 글자수 제한 없음)</strong>
<textarea id="unified-hook-sentence" rows="3" maxlength="1500"
    placeholder="예: 3주 써보니 아이 코막힘이 사라졌어요...">
```
프롬프트도 이걸 경험 데이터로 대접한다 — `src/promptLoader.ts:1362-1365`:
```
→ 도입부 첫 줄 또는 소제목1 첫 문장에 녹여라.
→ 이 문장은 사용자의 1차 경험 데이터이므로 QUMA/DIA+가 신뢰하는 신호다.
```

**그런데 두 군데서 죽는다.**

① **렌더러가 200자에서 자른다.** UI는 1500자, 정책 파일(`contentHookIntroPolicy.ts:17` `HOOK_INTRO_MAX_LINE_CHARS = 500` × 3줄)도 1500자인데:
```ts
// contentGeneration.ts:564
const hookHint = (hookInputEl?.value || '').replace(/\r\n/g, '\n').trim().slice(0, 200) || undefined;
// contentGeneration.ts:1183 동일
```
바로 위 `:561-562` 주석은 스스로 모순된다: `// 사용자 후킹 도입부 (선택, 최대 3줄·글자수 제한 없음)`.

② **앱이 권하는 예시 문장이 앱의 게이트에 걸린다.** placeholder의 `"3주 써보니 아이 코막힘이 사라졌어요"`는 `evidenceIntegrity.ts:33`의 세 번째 패턴에 정확히 매치된다:
```ts
/(?:한\s*(?:달|주|해)|\d+\s*(?:일|주|개월|달|년))\s*(?:동안\s*)?(?:써|사용|복용|신청|다녀|먹어)[^.!?\n]{0,20}/gi
```
`hookHint`는 `hasExplicitFirstPartyEvidence`의 세 경로 어디에도 없으므로(`personalExperience` 아님 / `FIRST_PARTY_METADATA_KEYS`(`:23-28`)에 없음 / 마커를 안 붙임 — `main.ts:5815-5818`은 `source.hookHint`만 세팅) → **사용자가 진짜 경험을 넣을수록 점수가 떨어진다.**

### 2-C. 본문이 나열이 되는 이유 — 칸이 '정보의 종류'로 정의돼 있다

**결정적 지시 1** — `seo/base.prompt:59-66`:
```
[의도 분석 → 답변 설계 매핑 (필수)]
- 키워드 받자마자 검색자의 진짜 질문 4개를 도출:
  Q1. 가장 궁금한 핵심 정보는?
  Q2. 함께 알고 싶어하는 부수 정보는?
  Q3. 결정/행동을 막는 의심/장벽은?
  Q4. 행동 후 후회 안 하려면 알아야 할 것은?
- Q1~Q4를 각 H2 1~4번으로 자동 매핑.
```
Q2가 **"부수 정보"** — 문제 해결과 무관한 정보를 넣으라는 명시 지시다. 그리고 "자동 매핑"은 상황 판단 없이 칸을 채우라는 뜻이다. 네 칸 어디에도 "이 사람이 지금 무엇에 막혀 있는가"가 없다.

**결정적 지시 2** — 소제목이 서술을 못 하게 막혀 있다. `src/contentJsonPromptFormat.ts:260`:
```
📌 [소제목 스타일 — 모든 모드 공통] headings[].title은 명사형·구 단위로 끝낸다
(예: "…가 갈린 이유", "…확인 포인트"). "…습니다/…해요/…했어요/…했다"처럼
완결 문장으로 끝나는 소제목 금지, 30자 이내.
```
명사구는 **상태를 이름 붙이는 문법**이다. 사건·변화·해결에는 서술어가 필요하다. 명사 라벨의 배열은 눈으로 봐도 목차다. `base.prompt:348`은 `"명사구·질문형·짧은 문장형을 내용에 맞게 섞고"`라고 정반대를 말하는데, JSON 포맷이 뒤에 오므로 이긴다.

**결정적 지시 3** — 각 섹션이 **독립 발췌 단위**로 7곳에서 못 박힌다: `base.prompt:116` R0-2 / `base:346` / `shared/exposure-structure.prompt:13`(`★ 이 첫 문장만 떼어내도 질문의 답이 되어야 한다(발췌 단위)`) / `human-writing-anti-pattern.prompt:36` / `official-exposure-rubric.prompt:27` / `promptLoader.ts:629-632` / `contentJsonPromptFormat.ts:43-49`의 `headings[]` 스키마(항목별 `summary`·`keywords`).

**반대 방향 지시는 문장·문단 안에만 있다** — `base.prompt:386-393`의 `[문장 연결의 황금률]`, `[문단 내부 계단식 심화]`. **섹션 간 나열을 막는 규칙은 base 어디에도 없다.** 그래서 "문장은 잘 이어지는데 글 전체는 목록"이 나온다.

### 2-D. 분량 압력이 나열을 기계적으로 강제한다

`base.prompt:121`:
```
R0-5. 본문 길이는 아래 지정된 목표 글자수(카테고리별 minChars, 보통 2,500~3,300자)에 맞춘다.
```
자료가 얇을 때 2,500자를 채울 길은 5개인데 4개가 막혀 있다:

| 확장 경로 | 상태 |
|---|---|
| 없는 사실 생성 | 차단 (`base:11-16` F1) |
| 일반론 채우기 | 차단 (`base:21-27` F3, 3회 초과 0점) |
| 경험 지어내기 | 차단 (`base:168-171` H1, `evidenceIntegrity.ts:157`) |
| 같은 말 반복 | 차단 (R0-5 자체) |
| **항목·하위질문 추가** | **열려 있고, 오히려 `(필수)` 지시** |

마지막 하나만 남는다. **정보나열은 부작용이 아니라 프롬프트가 남겨둔 유일한 합법 경로다.**

### 2-E. 8,000자짜리 진짜 사람 경험이 들어오는데 버려진다 ← 가장 큰 낭비

크롤러는 상위 노출 글 **본문**을 실제로 가져온다 — `src/sourceAssembler.ts:1619` (최대 5건 × 2,500자):
```
=== 상위 노출 글 본문 발췌 (사실 자료 — 수치·조건·절차는 이 자료 범위에서 사용) ===
```
**수집기가 스스로 용도를 "수치·조건·절차"로 좁힌다.** 자료의 대부분은 사람이 겪은 이야기인데, 모델은 거기서 숫자만 캐도록 지시받는다.

그리고 프롬프트의 마지막 말이 못을 박는다 — `evidenceIntegrity.ts:185`(이 블록은 최상위 선언), `:159`, `:176`:
```
이 블록과 충돌하는 앞선 규칙은 무효이며, 숫자 채우기·키워드 밀도·가짜 체험·감정어 개수를 맞추지 않는다.
- 입력 자료에서 확인되는 사실만 사용한다. 자료의 제3자 경험은 출처를 구분해 요약하고 작성자 경험으로 바꾸지 않는다.
- 검색 의도에 대한 짧은 답을 먼저 주고 조건·예외·절차·확인처로 깊이를 더한다.
```
전부 **"바꾸지 마라"**다. **"살려라"는 한 줄도 없다.**

**대조군이 같은 저장소 안에 있다.** 쇼핑커넥트에는 완성된 "살려라" 계약이 있다 — `src/prompts/affiliate/shopping_review.prompt:11-16`:
```
후기가 있을 때 가장 먼저 할 일
- 상품명과 기능을 다시 설명하기 전에, 구매자가 검색할 법한 골치 아픈 질문을 후기에서 뽑는다.
  예: 설치할 때 어디서 막혔는지, 소음이 어느 상황에서 거슬렸는지, 청소가 얼마나 번거로운지…
- 빈 칭찬보다 구체적인 설치·첫 사용·일상 사용·관리·고장·AS 경험을 우선한다.
- 같은 불편이 서로 다른 후기 2건 이상에 있을 때만 반복 의견으로 쓴다. 한 건이면 한 구매자의 의견으로 정확히 한정한다.
- 문단은 후기의 구체 상황 → 왜 구매 전에 중요한가 → 후기에 나온 해결·적응 또는 남은 한계 → 누구에게 맞고 안 맞는가로 이어 간다.
- 후기에서 해결 방법을 말하지 않았다면 상식으로 해결책을 만들어 넣지 않는다.
```
**SEO·홈판에는 이 6줄에 해당하는 것이 존재하지 않는다.** 가장 가까운 것은 `base.prompt:178-180`의 문체 템플릿뿐(`"여러 사용자 후기에서 반복적으로 보이는 패턴은"`) — *어떻게 말할지*는 있고 *무엇을 뽑을지*가 없다.

### 2-F. 상황 축은 이미 있는데, 무조건 할당량이라 오히려 환각을 만든다

`src/content/situationDepthContract.ts`는 실재하고 `contentGenerator.ts:2431`에서 **전 모드 무조건** 주입된다. 주석(`:11-13`)이 이미 정답을 적어 놨다:
> 직접 경험이 없어도 된다. 자료를 읽고 절차를 따라가 본 사람의 시선(간접 경험)이면 충분하다. 다만 **없는 경험을 지어내는 것은 금지**다.

근거 상태로 갈리는 건 `detailRule` **하나뿐**(`:34-51`). 나머지 4개 불릿은 조건절이 **없다** — `:59-62`, `:64-67`:
```
- [상황 분기] 같은 질문이라도 조건에 따라 답이 갈린다. 최소 2가지 상황을 나눠서
  각각의 답을 준다.
- [결정 지원] … 숫자만 나열하지 말고 그 숫자가 생활에서 뭘 뜻하는지 번역한다.
  (예: "6.9인치"가 아니라 "한 손으로 쥐면 위쪽 버튼에 손가락이 안 닿는다")
```
**자료에 갈림이 없어도 "최소 2가지"를 요구한다** → 모델은 조건을 만든다. 그리고 `:67`의 예시("손가락이 안 닿는다")는 자료에 없는 체감 판정을 **모범 답안으로 가르친다**. 프롬프트가 스스로 금지한 것을 예시로 시연하고 있다.

## 3. 해결 축 — 두 갈래

### (가) 사용자가 경험을 줄 때

**받는 방법은 이미 다 있다. 잠금만 풀면 된다.**

| 방법 | 코드 변경 | UI 변경 | 뒷단 변경 |
|---|---|---|---|
| ① hookHint 200자 캡 해제 | 2줄 (`.slice(0,200)` → `.slice(0,1500)`) | **0개** (HTML·정책이 이미 1500자) | 0줄 |
| ② SEO·홈판 경험 입력 개통 | 4줄 (모드 게이트 제거) | **+1개** (textarea 1개) | **0줄** (`main.ts`·게이트·프롬프트 전부 이미 지원) |

**쓰는 방법도 이미 다 있다.** ②를 하면 지금까지 한 번도 켜진 적 없는 계약 3개가 SEO·홈판에서 처음으로 도달 가능해진다:
- `situationDepthContract.ts:35-40` — 육하원칙 요구 + `⛔ 메모에 없는 시간·인원·금액·대기시간을 새로 만들지 마라`
- `evidenceIntegrity.ts:156` — `메모에 적힌 행동·기간·결과만 1인칭으로 쓰고 빈칸은 만들지 않는다`
- `seo/base.prompt:360` / `homefeed/base.prompt:16` — 13개 카테고리의 조건절이 처음으로 참이 됨

**UI 비용 명시:** ②는 통합 키워드 블록에 textarea 1개가 늘어난다(현재 `unified-hook-sentence` 바로 아래). 한 화면 기준 **+1개**. 비워두면 `|| undefined` → `if (personalExperience)` 미진입 → **기존과 100% 동일 동작**. 완전 옵트인.

**환각 위험:** 증가하지 않고 **감소한다.** 메모가 있어야만 1인칭이 열리고, 없으면 지금과 똑같이 잠긴다. 사용자가 준 사실이 늘수록 모델이 채울 빈칸이 준다.

---

### (나) 사용자가 아무것도 안 줄 때 ← **이쪽이 본론**

대부분의 사용자는 입력란을 비운다. 이 경우 **자료만으로 나열을 벗어나는 축**이 필요하다. 적대적 검증을 통과한 것만 남긴다.

모든 축의 공통 머리말은 **이 앱에 이미 있는 검증된 문형**을 쓴다 — `src/content/affiliateConversionStructure.ts:23-24`:
```
각 단계는 근거가 있을 때만 쓰고, 근거가 없으면
그 단계를 조용히 건너뛴다 — 건너뛴다고 쓰거나 근거 부족을 언급하지 않는다.
```
이 한 문장이 "지시 추가 = 환각 유발"을 끊는 유일한 장치다. 왜 필요한지 비유하자면 — 요리사에게 "4첩 반상을 차려라"라고 하면 재료가 없어도 접시 4개를 채운다. "재료가 있는 만큼만 차려라, 없다고 말하지도 마라"라고 해야 3첩이 나온다.

#### 축 A — 자료 속 타인 경험을 "살려라"로 전환 **(최우선, 정보나열의 직접 원인)**

지금은 8,000자의 사람 이야기가 들어와서 숫자만 추출되고 나머지는 폐기된다. affiliate에서 이미 검증된 추출 계약을 SEO·홈판용 **귀속형**으로 이식한다. 1인칭 전환 금지는 그대로 유지한다.

**지시문 전문:**
```
[자료 속 타인 경험 — 살릴 것과 살리지 말 것]
자료에 다른 사람이 겪은 이야기(후기·질문·사례)가 있을 때만 아래를 적용한다.
없으면 이 항목 전체를 조용히 건너뛴다 — 없다고 쓰지 않는다.

- 자료에서 먼저 뽑을 것은 숫자가 아니라 "어디서 막혔는가"다.
  어느 단계에서 걸렸는지, 무엇이 예상과 달랐는지, 어떤 조건에서 갈렸는지.
- 같은 지적이 서로 다른 자료 2건 이상에 있을 때만 "자주 나오는 지적"으로 쓴다.
  1건이면 그 한 사람의 의견으로 정확히 한정한다.
- 건수·비율·표본 크기는 쓰지 않는다.
- 문단은 [자료 속 구체 상황] → [왜 미리 알아야 하는가] → [자료에 나온 해결 또는
  남은 한계] → [누구에게 해당하고 누구에게 아닌가] 순으로 잇는다.
- 자료가 해결 방법을 말하지 않았다면 상식으로 해결책을 만들어 넣지 않는다.
  그때는 무엇을 어디서 확인해야 하는지까지만 쓴다.
- 이 내용은 전부 자료의 것이다. 작성자가 겪은 일로 바꾸지 않는다.
```

**환각 위험: 증가하지 않는다.** 전부 "자료에 있는 것을 뽑아라"이고, affiliate에서 검증된 안전장치 3종(2건 이상 규칙 / 해결법 창작 금지 / 1인칭 전환 금지)을 그대로 가져온다. `evidenceIntegrity.ts:159`의 "출처를 구분해 요약"과 정합한다.

**비용:** 프롬프트 +약 350자(≈150토큰, SEO 시스템 프롬프트 대비 0.5%). LLM 호출 0. UI 0.

#### 축 B — 상황 분기를 무조건 할당량에서 조건부로 전환 **(환각 감소가 주목적)**

현행 `situationDepthContract.ts:59-73`은 자료에 갈림이 없어도 "최소 2가지"를 요구한다. 이건 **개선이 아니라 현재 진행 중인 환각 압력의 제거**다.

**교체 전문 (`:59-73` 대체):**
```
- [상황 분기] 자료 안에 답이 갈리는 조건(대상·자격·기한·신청 경로·금액 구간·
  온라인/방문)이 2개 이상 명시돼 있으면, 그 갈림 하나를 소제목으로 세우고
  각각의 답을 따로 준다. 독자가 "내 경우는 어디에 해당하지?"를 찾을 수 있게.
  갈림이 자료에 없으면 만들지 마라. 그때는 조건 하나를 끝까지 파는 편이 낫다.
  ⛔ 분기 개수를 맞추려고 자료에 없는 조건(연령·동반자·긴급도)을 지어내지 않는다.

- [결정 지원] 자료 안에 같은 목적을 이루는 선택지가 둘 이상 있을 때만 비교한다.
  비교축은 자료에 값이 있는 항목(비용·기간·자격·필요 서류·처리 경로)만 쓰고,
  값이 없는 축은 표에서 뺀다.
  마무리는 우열 단정이 아니라 "어떤 조건의 사람에게 어느 쪽"으로 끝낸다.
  ⛔ 자료에 없는 체감·사용감으로 숫자를 번역하지 않는다.

- [좁고 깊게] 주제를 넓게 훑지 말고 자료가 실제로 다루는 상황 하나를 깊게 판다.
  넓은 개괄 3문단보다 좁은 상황 1개의 구체적인 해결이 낫다.

- [질문 선점] 자료 안에서 답할 수 있는 후속 질문이 보이면 1~2개를 본문에서
  미리 답한다. 자료로 답할 수 없는 질문은 던지지도 답하지도 않는다.
```
마지막 `⛔`가 현행 `:67`의 `"6.9인치가 아니라 한 손으로 쥐면…"` 예시를 대체한다. 그 예시는 삭제한다.

**줄 수 순증 0** (교체). 각 줄은 "없으면 결과가 달라지는가" 검사를 통과한다 — 각 `⛔`가 현행 무조건 요구를 실제로 끄기 때문이다.

#### 축 E — 독자 상황 재료를 SEO에도 공급 **(조건부, 선행 작업 필요)**

그런데 SEO만 빠져 있다 — `main.ts:5679`:
```ts
if ((situationMode === 'homefeed' || situationMode === 'business' || situationMode === 'mate') && situationKeywords.length > 0) {
```

**단, 그대로 열면 안 된다.** `main.ts:5681-5686`이 이 블록을 `source.rawText`에 **병합**하는데, `situationDepthContract.ts:26-28`이 `rawText.length >= 200`만으로 "자료 있음"을 판정한다:

```ts
function hasGroundingText(source?): boolean {
  return String(source?.rawText ?? '').trim().length >= 200;
```

## 8. 이 작업으로 달성되지 않는 것

**정직하게 적는다.**

1. **효과를 측정할 수단이 없다.** 노출 계측기가 고장나 있다 — SERP 파서(`analytics/dynamicSerpProbe.ts`)의 셀렉터가 현재 네이버 HTML과 안 맞고, 카드 0장에도 `fetchSuccess: true`를 반환해 **고장을 정상으로 기록**한다. 따라서 이 문서의 어떤 항목에 대해서도 "노출이 오른다 / 체류가 는다"고 말할 수 없다. 말할 수 있는 건 **"무엇이 달라지는가"까지**다.

2. **자료가 실제로 얇으면 여전히 나열이 된다.** 축 A~E는 전부 "자료에 있을 때만" 조건부다. 이건 의도적이다 — 조건을 풀면 환각이 된다. 그러나 그 대가로 **자료가 없는 글은 개선되지 않는다.** R0-5의 분량 압력(2,500자)은 그대로 남고, 유일하게 안 막힌 확장 경로가 여전히 "항목 추가"다. 이걸 근본적으로 풀려면 **"자료가 얇으면 짧게 끝내라"를 R0-5보다 상위에 두는 결정**이 필요한데, 그건 별도 판단 사항이고 이 문서 범위 밖이다.

3. **저비용 모델이 6만 자 프롬프트를 다 지키지 못한다.** 현재 assembled 프롬프트는 61,000~62,000자다. 여기에 지시를 더할수록 **강제력이 아니라 충돌 표면이 늘어난다**(실증: `promptLoader.ts:1215-1222`의 neoHook ↔ issue-story 상호 무력화). 그래서 이 플랜의 순증은 15줄로 묶고 나머지는 교체·삭제로 갔지만, **그 15줄이 실제로 지켜지는지는 라이브 생성물을 눈으로 보기 전까지 알 수 없다.**

4. **대부분의 사용자가 입력란을 비운다는 사실 자체는 해결되지 않는다.** R6를 해도 쓰는 사람만 쓴다. 그래서 (나) 축이 본론인 것이고, 그 축들은 전부 **"덜 나쁘게" 만드는 것**이지 "경험 있는 글"로 만드는 것이 아니다. 진짜 1차 경험이 없으면 진짜 1차 경험이 있는 글을 이길 수 없다.

5. **이 플랜은 이미 낡았을 수 있다.** 이 저장소는 하루에 여러 번 커밋된다 — 조사 시점 이후에도 `categoryTaxonomy.ts` 신설, 카테고리 프롬프트 교체 등이 들어갔다. **각 릴리즈 착수 직전에 해당 파일:라인을 다시 열어 확인할 것.** 특히 `seo/base.prompt`의 줄 번호는 다른 세션의 수정으로 어긋나기 쉽다.

6. **미검증으로 남긴 것** (인용 시 "확인됨"으로 쓰지 말 것):
   - 라이브 SERP 파싱 실패의 현재 재현 여부
   - `promptVariant` 결정 함수의 실제 런타임 값
   - R1~R4 적용 후 생성물이 실제로 어떻게 달라지는지 — **샘플 생성 전까지 미지수**
   - 지식iN 스니펫에 조건 분기가 실제로 얼마나 실리는지
