# SPEC-EVENT-RETRIEVAL-2026 — 현재 구조 실측

**작성**: 2026-09-10 / **방법**: 코드 전수 조사 + 사장님 실측 사례 1건

## 1. 사장님 실측 사례 (근거)

키워드 `김서현 류현진 평행이론` 으로 글을 만들었더니 서로 다른 세 사건이 한 글에 조립됐다.

| 수집된 자료 | 실제 사건 |
|---|---|
| 류현진 평행이론 기사 | 다른 시점·다른 맥락 |
| 송영진 151km 기사 | **완전히 무관** |
| 김서현 플레이오프 기사 | 중심 사건의 일부 |

사람이 검색했다면: `김서현` + `류현진` + `김영웅` 의 교집합에서
**"이틀 연속 김영웅에게 스리런"** 이라는 중심 사건에 도달한다.
`김영웅` 이 두 사건을 잇는 **다리 인물(bridge entity)** 이다.

## 2. 현재 파이프라인 (파일:줄번호)

```
키워드 → 검색 질의 1개 → 플랫폼 수집 → 주제 게이트 → 몫 제한 → 설계도 → 본문
```

- 재시도는 **같은 키워드로만** 한다 — `renderer/modules/contentGeneration.ts:1149`
  주석 원문: `// ✅ 같은 키워드로 재시도 (관련 없는 결과 방지 - 다른 키워드 사용 금지!)`
  이 결정은 그 자체로 옳다(엉뚱한 키워드로 새는 것을 막는다). 다만 **자료가 마른 경우의
  출구가 없다**.
- 크롤 예산 20초 — `FULLTEXT_COLLECT_BUDGET_MS`

## 3. 주제 게이트 — 4곳, 전부 같은 함수

`isOnTopicForKeyword` (`content/supplementTopicGuard.ts`) 가 4곳에 걸려 있다:

| 위치 | 단계 |
|---|---|
| `sourceAssembler.ts:1611` | 검색 결과 제목·설명 |
| `sourceAssembler.ts:1788` | 기사 본문 |
| `sourceAssembler.ts:7636` | 보충 자료 |
| `sourceAssembler.ts:8120` | 출구 게이트 |

`sourceAssembler.ts:8104-8118` 주석이 이 설계의 선행 기록이다:

> 그동안 들어오는 문을 하나씩 막았다… 막을 때마다 다른 문으로 들어왔다. 실측만 넷이다.
> 입구가 몇 개인지 모르는 채로 하나씩 막는 것은 끝이 없다.
> 어느 문으로 들어왔든 나갈 때 주제어가 없으면 버린다.
> **자료를 넣는 것이 강점인데 그 자료가 주제와 무관하면, 자료를 안 넣는 LLM 보다 못한 글이 나온다.**

`supplementTopicGuard.ts:215-228` 은 이 판정의 한계를 스스로 인정한다:

> isOnTopicForKeyword 는 토큰 2개면 통과시킨다. **그 판정 자체는 옳다** —
> 실외기 화재 기사도 실제로 아파트와 베란다를 말하므로 버릴 근거가 없다.
> 게이트를 조이면 자료가 마른다. 대신 **머리 명사**를 본다 … 곁가지는 몫만 제한한다.

## 4. 구조적 공백 — 두 개

### 공백 A: 판정이 **어휘**뿐이다
게이트 4곳이 전부 토큰 겹침 + 머리 명사다. 그래서 **같은 낱말을 쓰는 다른 사건**은
구조적으로 통과한다. 송영진 기사에도 `류현진`·`151km`·야구 어휘가 들어 있다.

어휘를 더 조여도 못 푼다 — 조이면 자료가 마르고(위 주석이 이미 겪었다),
느슨하면 다른 사건이 들어온다. **축이 다르다: 사건 동일성이 필요하다.**

### 공백 B: 자료가 마를 때의 **출구가 없다**
황금키워드는 정의상 "검색량은 오는데 문서가 아직 적은" 상태다.
지금은 같은 키워드로 재시도할 뿐이고, 재시도해도 없는 문서는 없다.
그 결과 주변 자료로 LLM 이 억지 조립을 한다.

## 5. 이미 있는 재사용 부품

**전부 순수 함수이고 export 되어 있다.** 새로 만들 것이 생각보다 적다.

| 부품 | 위치 | 뽑는 것 |

# Phase 0 실측 결과 (2026-09-10) — **초안의 핵심 가정이 틀렸다**

방법: 저장된 발행 글 150편(`content-policy-articles.json`) 재계산. 유료 호출 0.
자료 원문은 저장되지 않으므로, 결과물(본문)에서 억지 조립의 자국을 쟀다.

## 발견 1 — 인물명 추출기는 **존재하지 않는다** (치명)

초안은 `extractVerifiableClaims` 가 인물을 뽑는다고 적었다. **틀렸다.**

```
fabricationCheck.ts:52  const PEOPLE = /\d[\d,]*\s*(?:명|가구|세대|팀)/gu
fabricationCheck.ts:59  KIND_LABEL.people = '인원'
```

`people` 은 **인원수**(40명·3가구)다. 인물명이 아니다. 코드베이스 어디에도 인물명
추출기가 없다(성씨 사전·NER grep 0건).

실측(블랙핑크 글 7섹션): `지수·로제·리사·제니` 가 본문·소제목에 있는데 `people=[]`.
유일하게 잡힌 것은 `"40명"` 이었다.

## 발견 2 — 3자 토큰은 인물이 아니라 **일반명사**를 뽑는다

`extractKoreanFactTokens` 의 3자 토큰 실측:

| 글 | 뽑힌 3자 토큰 |
|---|---|
| 블랙핑크 | 소속사 · 스케줄 · 플랫폼 · 블링크 · 멤버들 · 아쉬움 |
| 거제 여행 | 근포마 · 주차장 · 화장실 · 포토존 · 해산물 · 매미성 |
| 한다감 | 화장실 · 사생활 · 시험관 · 초음파 · **한다감** · 삼청동 |

인물이 섞여 나오긴 하나(`한다감`), 일반명사가 압도적이다. 이 목록으로 사건 서명을
만들면 **섹션마다 다른 일반명사**를 갖게 되어 전부 "고아"로 판정된다 — 실제로 1차
측정에서 여행 글이 4/4 고아로 나왔다.

## 발견 3 — 데이터 기반 공통어 사전(DF)도 이 규모에선 안 된다

150편에서 문서 빈도를 세어 공통어를 자동 판별해 봤다.

```
화장실 DF=3 → 고유어(유지)   ← 걸러져야 하는데 남는다
매미성 DF=5 → 공통어(제외)   ← 남아야 하는데 걸러진다
```

표본이 적고 주제가 흩어져 DF 가 신호를 못 만든다. 더 큰 코퍼스가 필요하고,
그건 이 SPEC 의 범위를 넘는다.

## 결론 — Phase 1 을 다시 설계해야 한다

초안 Phase 1 은 "이미 있는 순수 함수를 조립하면 비용 0" 이었다. **성립하지 않는다.**
쓸 수 있는 것은 **날짜뿐**이다(`DATE` 정규식은 실제로 동작 — "8월 3일" 확인).
인물 축이 없으면 사건 동일성 판정이 서지 않는다.

### 선택지

| 안 | 내용 | 비용 | 한계 |
|---|---|---|---|
| A. 날짜 축만 | DATE 정규식만으로 판정 | 0 | 날짜 0~1개인 글이 다수 → 신호 부족 |
| B. 성씨 사전 | 한국 성씨 ~50개 + 이름 패턴 | 0 | 예명(제니·리사) 못 잡음. 뉴스 사건에는 충분 |
| C. **설계도 필드 추가** | 이미 도는 Blueprint LLM 호출 스키마에 `centralEvent` 추가 | **≈0 (한계비용)** | 설계도 실패 시 폴백 필요 |

**권장: C + B(폴백).**
`SPEC-BLUEPRINT-2026` 의 설계도 호출이 이미 `offTopic[]` 을 포함한 JSON 을 만든다
(`content/blueprint/blueprintSchema.ts:37`, 호출 `contentGenerator.ts:6200`).
여기에 `centralEvent { people[], dates[], eventType }` 필드 하나를 더하는 것은
**새 호출이 아니라 기존 요청의 필드 추가**라 한계비용이 사실상 0이다.
그리고 "이 기사에 누가 나오는가" 는 정규식보다 LLM 이 압도적으로 잘한다.

판정(배제 규칙)은 그 서명을 받아 **순수 함수**가 한다 — LLM 에게 판정을 맡기지 않는다.

## 측정 도구의 한계 (정직하게)

이번 측정은 **결과물**에서 자국을 쟀지 자료 자체를 재지 못했다. 자료 원문이 저장되지
않기 때문이다. 자료 단계의 곁가지 비율을 실측하려면 수집 자료를 남기는 계측이 먼저다
(디버그 덤프, 옵트인). 그 전까지 개선 폭은 **결과물 기준으로만** 말할 수 있다.
